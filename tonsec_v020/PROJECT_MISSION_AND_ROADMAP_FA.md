# مأموریت و نقشه‌راه اصلی TON Security Engine

آخرین به‌روزرسانی: 2026-11-04
نسخه پروژه: 0.2.0
وضعیت: توسعه فعال؛ آماده‌سازی برای آزمون واقعی گسترده

---

## 1. مأموریت اصلی پروژه

TON Security Engine باید به یک موتور مستقل، خودکار و مقیاس‌پذیر ممیزی امنیتی اکوسیستم TON تبدیل شود.

هدف بررسی یک قرارداد منفرد یا اجرای چند تست دستی نیست. هدف، بررسی خودکار صدها یا هزاران پروژه TON با یک فرمان و تولید گزارش جامع و قابل ارزیابی است.

ورودی موتور باید مسیر یک مجموعه پروژه، مخزن یا سورس باشد.

موتور باید خودش:
- پروژه‌ها و فایل‌های مرتبط با TON را کشف کند.
- پروژه‌ها و زبان‌های برنامه‌نویسی را شناسایی و دسته‌بندی کند.
- قراردادها، Walletها، توابع و ارتباطات آن‌ها را تحلیل کند.
- مسیرهای انتقال TON، Jetton و NFT را بررسی کند.
- کنترل مالکیت، مجوزها، امضا و Replay را ارزیابی کند.
- پیام‌های ورودی و خروجی و Extensionها را بررسی کند.
- رفتار عادی، تفویض اختیار معتبر، رفتار مشکوک و آسیب‌پذیری احتمالی را تفکیک کند.
- یافته‌ها را با شواهد، محل دقیق، شدت، اطمینان و محدودیت‌ها گزارش کند.
- نتایج تمام پروژه‌ها را در یک گزارش تجمیعی ارائه دهد.

## 2. الزامات غیرقابل‌تغییر

1. اجرای نهایی باید با یک فرمان انجام شود.
2. تحلیل پروژه‌ها باید خودکار باشد؛ کاربر نباید برای هر بررسی فرمان جداگانه اجرا کند.
3. موتور باید مستقل از Sentinel باشد.
4. خروجی خام Sentinel و TON Security Engine باید مستقل بماند؛ مقایسه فقط پس از تحلیل مستقل انجام شود.
5. اجرای اسکن محلی باید فقط‌خواندنی باشد؛ تولید گزارش مجاز است.
6. تحلیل ناقص نباید کامل معرفی شود.
7. یافته heuristic نباید به‌عنوان آسیب‌پذیری اثبات‌شده گزارش شود.
8. شواهد، شدت، اطمینان، محدودیت و موارد خارج از توان باید صریح باشند.
9. توسعه باید با شواهد آزمون واقعی هدایت شود، نه صرفاً افزایش تعداد تست‌های مصنوعی.

## 3. زبان‌ها و حوزه‌های تحلیل

زبان‌های هدف:
- FunC
- Tolk
- Tact
- سایر منابع مرتبط با TON در محدوده پشتیبانی‌شده

حوزه‌های امنیتی:
- Authorization و مالکیت
- Signature و Replay protection
- Seqno، nonce و valid_until
- پیام‌های ورودی و خروجی
- انتقال دارایی و مسیرهای ارسال
- Jetton و NFT
- Wallet و Extension security
- کنترل زمان و اعتبارسنجی ورودی
- ارتباطات بین‌تابعی
- جریان کنترل و داده
- در مراحل بعدی تحلیل TVM bytecode

## 4. روش قطعی توسعه و آزمون

ترتیب صحیح کار:

1. ابتدا موتور موجود بدون تغییر کد روی یک مجموعه واقعی و متنوع از پروژه‌های TON اجرا شود.
2. اجرای baseline و نتایج خام ثبت شوند.
3. پوشش فایل‌ها و زبان‌ها، خطاها، زمان اجرا و پروژه‌های ازدست‌رفته اندازه‌گیری شوند.
4. یافته‌ها به‌صورت مستقل ارزیابی شوند:
   - True Positive
   - False Positive
   - False Negative
   - موارد نامشخص
5. شکاف‌ها و مشکلات واقعی اولویت‌بندی شوند.
6. اصلاحات فقط بر اساس شواهد آزمون انجام شوند.
7. همان مجموعه آزمون مجدداً اجرا شود.
8. بهبود با نتایج قبلی مقایسه و مستند شود.

آزمون یک قرارداد منفرد جایگزین آزمون گسترده مجموعه پروژه‌ها نیست.

توسعه Parser، Call Graph، CFG و Data Flow نباید بدون ارتباط با نیاز یا خطای مشاهده‌شده در آزمون واقعی به اولویت تبدیل شود.
